# 팀 문서 Phase 관리 규칙

## 목적

작업 내용을 하나의 큰 Markdown 파일에 계속 추가하지 않는다. 담당자별로 Phase를 나누고, 한 Phase의 목표·체크리스트·결과만 해당 파일에 기록한다.

## 폴더 구조

```text
phases/
├── phase_01_*.md
├── phase_02_*.md
└── ...
```

이 폴더에는 현재 담당 영역의 Phase 파일만 둔다. 다른 담당 영역의 Phase를 복사하거나 한 파일에 여러 Phase의 작업을 섞지 않는다.

각 Phase의 상태는 Phase 문서와 분리된 status 파일에 기록한다.

```text
phases/
├── phase_01_input_policy.md
├── phase_01_status.md
├── phase_02_risk_segments.md
├── phase_02_status.md
└── ...
```

## Phase 파일 기본 형식

```markdown
# Phase 01: 제목

## 목표

이번 Phase에서 끝낼 일을 한 문장으로 쓴다.

## 참고 문서

- 팀 공통 `AGENTS.md`
- 담당자 전용 `AGENTS.md`
- 관련 노션 담당 페이지
- 관련 로컬 spec 문서

## 해야 할 일

- [ ] 작업 1
- [ ] 작업 2

## 입력과 출력

```json
{}
```

## 변경 파일

- 아직 없음

## 검증 방법

- 실행 방법
- 확인할 결과

## 작업 결과

완료 후 실제 결과를 적는다.

## 남은 문제

없으면 `없음`이라고 적는다.

## 다음 Phase로 넘길 내용

다음 담당자나 다음 Phase가 바로 사용할 내용을 적는다.
```

## 운영 규칙

## 모든 Phase 개발 작성 방식

앞으로 모든 Phase는 아래 순서로 작성하고 실행한다.

1. Phase 문서에 `해야 할 일` 체크리스트를 먼저 둔다.
2. 체크리스트의 작업을 실제 코드로 구현한다.
3. 구현한 코드의 실행 방법과 테스트를 확인한다.
4. 구현하지 못한 항목은 체크하지 않고 남은 문제로 기록한다.
5. Phase가 끝나면 status에 실제 개발 내용을 요약한다.

Phase 문서는 설계 설명만 적는 파일이 아니다. 실제로 만들 코드의 작업 목록과 입력·출력·검증 방법을 적는 작업 문서다.

실제 실행 코드는 프로젝트 루트 `app/` 폴더에 작성한다. 담당 영역 폴더인 `agent/`에는 담당 지침, overview, Phase 문서, status만 둔다. 실행 코드·샘플 입력·테스트는 Phase 문서와 같은 폴더에 두지 않는다.

모든 함수는 기능별로 작게 나누고, 상위 함수 또는 클래스 메서드가 하위 함수를 조합한다. 각 함수·메서드 선언 바로 위에는 역할을 설명하는 한국어 한 줄 주석을 붙인다.

## status 작성 방식

status의 `현재 사항`은 구현한 함수명과 역할을 핵심만 쉽게 쓴다.

- `함수명`: 함수가 맡은 역할
- 실행 또는 테스트 결과가 있으면 한 줄로 기록

예시:

```markdown
## 현재 사항

- `build_notion_markdown`: Agent 분석 결과와 원본 메시지를 받아 Notion용 Markdown 문자열을 만든다.
- `build_evidence_messages_table`: 근거 메시지를 표 형태로 만든다.
- `run_phase_04`: 샘플 데이터를 넣고 Markdown 결과 파일을 생성한다.
- 테스트 12개가 통과함.
```

현재 사항에는 긴 배경 설명, 설계 철학, Phase 문서 내용의 반복을 쓰지 않는다. `문제/막힌 지점`에는 실제로 실행을 막은 문제만, `결정된 사항`에는 코드를 작성하면서 확정한 내용만 쓴다.

Phase 문서는 status와 맞춰 `해야 할 일` 체크리스트 중심으로 갱신한다. 완료한 구현 항목은 체크하고, 구현하지 못한 항목은 체크하지 않는다.

- 한 번에 하나의 Phase만 `진행 중`으로 둔다.
- 코드를 작성하기 전에 해당 Phase 문서에 환경, 폴더 구조, 입력·출력 계약, 테스트 범위를 먼저 기록하고 합의한다.
- 합의되지 않은 런타임, 프레임워크, 폴더, 테스트 파일을 임의로 만들지 않는다.
- 구현하지 않은 내용을 완료로 표시하지 않는다.
- Phase가 끝나면 테스트 결과와 실패 사례를 남긴다.
- 공통 계약을 바꾸면 관련 담당자의 Phase 문서와 노션 기준을 함께 확인한다.
- Phase 파일에 새 요구사항이 생겼다고 전체 문서를 복사해 붙이지 않는다. 다음 Phase 파일을 만든다.
- 노션과 사용자 결정이 바뀌면 해당 Phase 문서의 참고 기준과 변경 이유를 업데이트한다.
- 완료된 Phase는 삭제하지 않고 기록으로 보존한다.

## status 파일 운영 규칙

- Phase를 시작하는 즉시 해당 `phase_XX_status.md`를 만든다. 이미 있으면 최신 내용으로 갱신한다.
- Phase가 진행되는 동안 상태 변화, 문제 또는 막힌 지점, 결정 사항이 생기면 status 파일을 갱신한다.
- Phase가 끝나기 전에 최종 내용을 status 파일에 기록한다.
- status 파일은 아래 세 항목만 사용한다.

```markdown
## 현재 사항

## 문제/막힌 지점

## 결정된 사항
```

- 각 항목에 내용이 없으면 `없음`이라고 쓴다.
- Phase 설명, 체크리스트, 긴 작업 로그를 status 파일에 복사하지 않는다.
