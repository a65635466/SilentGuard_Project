## 1. Agent의 역할

Agent는 모델의 숫자를 사람이 검토할 수 있는 설명과 알림으로 바꾼다.

```text
원본 메시지 + 모델 결과 + 위험도
-> 위험 메시지 분석
-> 위험 구간 구성
-> 위험 사건 구성
-> 위험 유형·근거·이유 작성
-> 관리자 요약·누락 맥락·초기 조치 작성
-> 표준 알림 JSON 반환
```

Agent가 반드시 판단하는 것:

- 어떤 메시지가 위험 신호와 관련 있는지
- 이어지는 메시지를 하나의 위험 구간으로 묶을지
- 떨어진 위험 구간을 하나의 사건으로 볼지
- 위험 유형과 근거 메시지 ID
- 관리자에게 보여줄 설명과 추가 확인 사항

Agent가 확정하지 않는 것:

- 학교폭력 여부
- 가해자·피해자 관계
- 실제 의도
- 과거에 일어난 사실
- 처벌이나 징계

## 2. 위험 구간 판단 기준

같은 구간으로 묶는 경우:

- 같은 사람을 향한 발언이다.
- 같은 주제의 대화가 계속된다.
- 시간 간격이 짧다.
- 배제, 조롱, 압박, 협박이 연속된다.
- 여러 사람이 같은 사람을 함께 압박한다.

다른 구간으로 나누는 경우:

- 시간이 많이 떨어져 있다.
- 주제가 바뀌었다.
- 대상이 달라졌다.
- 이전 대화가 끝난 뒤 새로운 흐름이 시작되었다.

판단 결과에는 반드시 원본 메시지 ID와 시간을 연결한다. 위험한 한 줄만 떼지 말고 이해에 필요한 주변 메시지도 구간에 포함한다.

## 3. 사건 구성 기준

여러 위험 구간을 하나의 `incident`로 묶을 때는 다음을 확인한다.

- 같은 채팅방인가
- 같은 대상 또는 관계 흐름인가
- 위험 유형이 비슷한가
- 시간상 완전히 무관하지 않은가

근거가 부족하면 억지로 하나의 사건으로 묶지 않는다. 하나의 구간 또는 검토 필요 상태로 반환하고 `missing_context`에 이유를 적는다.

## 4. 표준 알림 필드

필드 이름을 임의로 바꾸지 않는다.

```json
{
  "incident_id": "incident_room_20260812143005_a1b2c3_001",
  "risk_chat_segments": [],
  "suspected_risk_types": [],
  "context_reason": "",
  "evidence_message_ids": [],
  "manager_summary": "",
  "missing_context": [],
  "recommended_initial_actions": [],
  "disclaimer": "자동 분석된 위험 신호이며 최종 판단이 아닙니다."
}
```

각 필드 규칙:

- `incident_id`: Agent가 구성한 사건 추적용 ID
- `risk_chat_segments`: Agent가 묶은 구간과 원본 메시지 ID·시간
- `suspected_risk_types`: 원문에서 확인되는 위험 유형만
- `context_reason`: 실제 표현, 이어진 흐름, 추가 확인이 필요한 이유
- `evidence_message_ids`: 입력에 실제 존재하는 메시지 ID만
- `manager_summary`: 관리자용 2~4문장 요약
- `missing_context`: 확인할 수 없는 사실과 추가 확인이 필요한 정보
- `recommended_initial_actions`: 처벌이 아닌 확인·보존·도움 요청 안내
- `disclaimer`: 자동 분석이며 최종 판단이 아니라는 문구

## 5. 위험 유형

원문에서 확인되는 유형만 선택한다.

- 반복성
- 표적성
- 집단성
- 배제성
- 위협성
- 공개성

유형을 넣을 때는 근거 메시지 ID를 함께 연결한다. 원문에 없는 유형을 모델 점수만으로 추가하지 않는다.

## 6. 입력·출력 계약

백엔드 입력:

```json
{
  "analysis_id": "analysis_room_20260812143005_a1b2c3_20260812143100_d4e5f6",
  "room_id": "room_20260812143005_a1b2c3",
  "bullying_probability": 0.91,
  "risk_level": "immediate",
  "messages": [
    {
      "message_id": "msg_001",
      "sender_id": "A",
      "sender_label": "A",
      "text": "너 왜 또 여기 들어왔냐",
      "created_at": "2026-08-08T14:28:00+09:00"
    }
  ]
}
```

`analysis_id`는 백엔드가 생성하는 분석 요청 추적용 ID이며 사건을 의미하지 않는다. `incident_id`와 사건 구성은 Agent가 원본 문맥을 분석한 뒤 출력에서 생성한다.

출력은 반드시 JSON으로 받는다. JSON이 깨지거나 필수 필드가 없으면 재시도하거나 안전한 기본 응답을 사용한다.

## 7. 안전한 표현 규칙

사용할 표현:

- 위험 신호가 보입니다.
- 괴롭힘 가능성이 있어 추가 확인이 필요합니다.
- 원문상 배제와 압박의 흐름이 확인됩니다.
- 자동 분석 결과이며 최종 판단이 아닙니다.

사용하지 않을 표현:

- A는 가해자입니다.
- B는 피해자입니다.
- 이것은 학교폭력 사건입니다.
- 반드시 처벌해야 합니다.
- A가 악의적으로 행동했습니다.

원문 사실과 Agent 해석을 분리해서 작성한다. 확인하지 못한 의도나 과거 사건을 만들어내지 않는다.

## 8. 출력 검증

외부 알림이나 프론트엔드에 넘기기 전에 다음을 확인한다.

- [ ] 필수 필드가 모두 있는가
- [ ] 모든 근거 ID가 입력에 있는가
- [ ] 원본 문장이 바뀌지 않았는가
- [ ] 원본 시간과 ID가 보존되었는가
- [ ] 확정 판정 표현이 없는가
- [ ] 가해자·피해자를 확정하지 않았는가
- [ ] 입력에 없는 의도와 사건을 추가하지 않았는가
- [ ] `disclaimer`가 있는가

검증 실패 시 외부 전송을 막고 `notification_failed` 또는 검증 실패 상태를 반환한다.

## 9. 외부 알림 연결

MCP와 외부 채널은 분석하지 않는다. 검증이 끝난 표준 알림만 전달한다.

```text
입력: analysis_id + room_id + room_name + notification_email + incident + messages
출력: channel + status + sent_at + external_message_id + notion_url + recipient_email
```

첫 MVP에서는 다음처럼 둔다.

```json
{
  "channel": "none",
  "status": "not_configured",
  "sent_at": null,
  "external_message_id": null,
  "recipient_email": "teacher@example.com"
}
```

## 11. 함수 작성 규칙

- 기능별로 작은 함수로 나눈다.
- 상위 함수 또는 클래스 메서드가 작은 함수들을 조합한다.
- 모든 함수·메서드 선언 바로 위에 역할을 설명하는 한국어 한 줄 주석을 붙인다.
- 입력 검증, OpenAI 호출, 결과 변환, 출력 검증을 한 함수에 섞지 않는다.

Phase 문서 위치:

`phases/`

분석 기준, 프롬프트, JSON 스키마, 검증 규칙을 한 문서에 모두 몰아넣지 않는다. Phase별 파일을 하나씩 진행하고, 변경 이유와 실패 샘플을 해당 Phase에 기록한다.

각 Phase를 시작할 때 `phases/phase_XX_status.md`를 자동으로 만든다. status 파일은 아래 세 항목만 사용한다.

```markdown
## 현재 사항

## 문제/막힌 지점

## 결정된 사항
```

Phase 진행 중에는 상태가 바뀔 때마다 갱신하고, Phase 종료 직전에 최종 상태를 기록한다. 문제가 없거나 결정된 내용이 없으면 각 항목에 `없음`이라고 쓴다. 체크리스트나 긴 설명은 Phase 본문에 두고 status 파일에는 반복하지 않는다.
